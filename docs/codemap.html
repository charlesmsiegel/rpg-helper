An offline, on-device tabletop RPG reference whose one guarantee is that a quote and a paraphrase are never confusable

generated 2026-07-31 · analysed at 0c217cb · 165 source files, 36,130 LOC (28,073 Kotlin) · 11 Gradle modules

Ludex RPG is a refusal engine with a quoting front end.

An offline Android/JVM assistant for tabletop roleplaying: it answers rules questions by reproducing the book's bytes under a resolved citation, answers setting questions in generated prose whose every claim is chip-cited back to a passage, and tracks characters against constraints the book itself declares. Everything runs on the device; the only socket the app ever opens is the model download.

The whole architecture serves one sentence, stated in README.md:9 and again in docs/THEORY.md: a quote and a paraphrase must never be confusable, anywhere in the app. That is not a policy enforced by review — it is compiled into the data. A pack chunk carries origin (source vs derived) and kind, and Router.route partitions on exactly those two columns (routing/src/main/kotlin/dev/ludex/routing/Router.kt:96-123). Nothing asks a model "is this a rules question?"

Architecturally it is a strictly layered multi-module Gradle build: eleven Kotlin modules, one root (:pack) that owns the untrusted file format and its gate, and two thin surfaces (:cli, :app) that render the same Answer. The dependency scan found zero cycles at both module and file level across 253 import edges.

Three flows carry essentially all of this system's correctness risk: asking a question (where the quote/paraphrase guarantee is either kept or broken), installing and activating a pack (where a crash can leave the shelf lying about what is on it), and borrowing a pack file while someone uninstalls it (where an answer can cite a book that no longer exists). The fourth — the model download — is the only place bytes enter from the network, and is summarised at the bottom.

Seams this flow exposes

SeamWhereWhat it costs if it moves
The cache is consulted before routing, not aftersession/…/AskService.kt:112-136Routing is what invokes the model. A lookup afterwards has already paid the cost it exists to avoid. The precondition — "could route 3 fire at all?" — is computed from candidate columns, not from the model.
The feed is written after the answer existssession/…/AskService.kt:158A query that throws must not leave a turn in the window with nothing under it, because that turn is what the next follow-up resolves against.
Cache stores a render, not cardssession/…/AskService.kt:26-35, state/…/AnswerCache.kt:126-132Re-assembling cards from a cached body would be a second rendering under possibly different code — exactly what contractVersion exists to prevent. Consequence: Asked.answer is null on a hit, and any caller reaching into it must handle that.
Route 3 firing ≠ route 3 succeedingsession/…/AskService.kt:150-156Redaction can empty the context and an unresolvable citation suppresses the card. Caching those would serve a degraded answer for as long as the key lives. Guarded by answer.cards.any { it is Card.Generated }.
A throwing generator costs the generated card and nothing elserouting/…/Router.kt:342-346, 361-364Both residualIntent and answer are wrapped in runCatching. Letting either escape would discard the quote cards the same question already produced correctly.
Citation resolution is all-or-nothingrouting/…/Router.kt:397-408A card listing some of the passages it found is indistinguishable on screen from a complete one. Any refactor that turns resolveAll into a mapNotNull breaks the product's central claim silently.
Redacted text is carried, never recomputedretrieval/…/Pipeline.kt:63-72, routing/…/Router.kt:410-418The lexical independence test read this exact string. A second implementation downstream was present once and disagreed — it inserted a different marker.
Redaction failure is not a refusalrouting/…/Router.kt:315-329Route 3 fired, so the user gets a ModelUnavailable card listing passages — never a model answering from an empty context, which is pretraining wearing the generated card's styling.
The context budget counts every field, not just the body. routing/…/Router.kt:294-295 charges redactedText and headingPath against the 16 KiB ceiling. This was a real defect: five chunks with one-line bodies and enormous heading paths cleared the budget while expanding the prompt by tens of megabytes. Any new field passed to the generator must be added to this sum, and nothing in the type system enforces that.

Flow 4 — the model download, in brief

The app's only network operation (model/…/ModelDownloader.kt:42). Four properties worth knowing:

  • Partials are dot-prefixed (.name.partial, :69) so no final name can ever be spelled like a partial — a manifest holding both weights and weights.partial would otherwise have the first file's verified bytes occupy the second's partial path.
  • Verification is over the assembled whole, not the fetched tail (:130) — a resume stitched onto a corrupt prefix would otherwise pass. Size is checked too (:140), because a digest match on a short file is not one.
  • A move failure keeps the verified partial (:152-159) and says where, rather than discarding gigabytes that hashed correctly.
  • ModelManifest refuses a placeholder digest at parse time; the make-manifest subcommand exists so that refusal stays tenable.

Ownership here is unusually clean — the interesting question is what leaks around it.

Every table in state.db has exactly one writing class. Every module dependency points down a strict layering with no cycles at module or file level (253 import edges scanned). The two boundary problems that do exist are both process-global mutable state in companion object/object singletons, and one of them silently changes what a second Store in the same process would see.

Boundary observations

1. Library holds a process-global supersession cache in its companion object. session/src/main/kotlin/dev/ludex/session/Library.kt:131-147 keeps a single (fingerprint → SupersededSet) entry, @Synchronized, shared by every Library instance in the JVM — including ones opened from different Store roots. Correctness survives because the key is a content fingerprint (pack_uid, file_sha256), so identical keys imply identical bytes. But it is module-level state reached from an instance path, it is invisible at the call site, and it makes tests order-dependent in a way nothing declares. The comment justifies the single entry, not the global placement.
2. Storage is a never-closed process singleton, and that is the fix for a worse bug. app/src/main/kotlin/dev/ludex/app/Storage.kt:27-40. Each surface used to build its own Store, and PackLibrary's initializer calls reconcile() — which cannot tell died mid-flight from happening right now, so opening Documents during an install destroyed the install. The singleton is correct; the fragility is that the invariant it now carries ("exactly one Store per process") is enforced by nothing but this object, and any code path that constructs Store(...) directly re-opens the hole. :cli does construct Store directly (Main.kt), which is safe only because it is a one-shot process.
3. The Android boundary is genuinely clean. No module below :app imports an Android class; :app's own MainActivity.kt:44-50 claims this as the point of the layering rather than an accident, and the module graph bears it out. The one place it nearly broke is recorded in StateDb.kt:20-26: the write path was on sqlite-jdbc, whose natives cannot load on Android, so constructing AskViewModel killed the app at startup. Both directions now use the same bundled SQLite.
4. :cli is deliberately the one module that depends on all the others. cli/build.gradle.kts:15-16 states the rationale: it is the wiring, and every seam it crosses is a seam the app will have to cross too. Its 22 outbound file imports make it the highest fan-out file in the repo — expected for this role, not a smell.
5. Raw SQL string interpolation exists, and is bounded. Three places build SQL by concatenation rather than binding: retrieval/…/Pipeline.kt:324-326 (alias phrases, single-quote-escaped, drawn from a tokenizer whose separators include punctuation), Pipeline.kt:371,401 (chunk ids, typed Long), and state/…/Conversation.kt:75 (windowSize, a constant). None is currently injectable, but the alias path is the one a future change could make so — it is the only one whose interpolated value originates in user text.

The pack format is pinned by test. The answer contract is pinned by memory.

This codebase is unusually good at enforcing its own rules — the pack schema is checked against its spec document by SchemaDocSyncTest, the float16 codec is verified across all 65 536 bit patterns, and one deliberately-corrupted pack exists per rejection the app promises to make. Against that standard, one invariant stands out for having no mechanical enforcement at all: AskService.CONTRACT_VERSION. It is referenced by nothing outside the two files that define and consume it, no test asserts it, and forgetting to bump it makes an upgraded app serve cached cards built under rules it no longer follows.

Concurrency

Four primitives, and the model is small enough to hold in your head:

  • StateDb.lock (StateDb.kt:44) — reentrant, serializes every use of the single SQLite connection, with a depth counter so a nested transaction joins rather than committing the outer one early.
  • PackLibrary.leaseLock (PackLibrary.kt:154) — guards readers and pendingDeletion together. Nested above StateDb.lock.
  • Library.supersessionCache (Library.kt:131-147) — @Synchronized, process-global, one entry. A race costs one redundant scan, never a wrong answer, because the key is a content fingerprint.
  • ModelRuntime registry (ModelRuntime.kt:59,65) and the download's AtomicBoolean cancel flag.

Everything else is confined: retrieval and routing are pure functions of an ActiveSet and a Retrieved, holding no mutable state between calls. All ViewModel work runs on Dispatchers.IO inside viewModelScope and writes state back on the main dispatcher.

Risk ranking

1. CONTRACT_VERSION is a hand-maintained cache invalidator with no guard. session/…/AskService.kt:172. Cached cards are stored already rendered and persist across upgrades. Change a gate, a prompt, the routing partition or the card's serialized form without bumping it, and the app serves answers built under rules it no longer follows — indistinguishable on screen from fresh ones. Worse, the retrieval gates are not in the key at all (session/…/Library.kt:46), so a calibration change is a silent one by default. A test that hashes the concatenation of every contract-shaping constant and fails when it changes without a version bump would close this for a few dozen lines.
2. CI does not run the test suite the README says it runs. .github/workflows/ci.yml:35 runs ./gradlew :pack:test; README.md ("Building") says CI "runs the same command" as ./gradlew test. Of 750 tests across 11 modules, CI covers :pack only. Compounding it, the workflow is workflow_dispatch-only by deliberate choice (documented at :3-15) — so today nothing runs on any push or pull request. The trigger decision is defensible and explained; the :pack:test-vs-test gap looks like an oversight, and it is the one that will bite when the trigger is restored.
3. Byte-exactness of a quotation is a doc comment below the router. routing/…/Cards.kt:27-33 forbids passing Card.Verbatim.body through any rich-text renderer, and RenderParityTest checks the two current surfaces agree — but the type is a plain String, so nothing stops a third surface, or a Compose refactor, from re-wrapping or markdown-parsing it. This is the product's central guarantee with the weakest mechanical backing of any invariant here. A value class Verbatim(val bytes: String) would make the mistake unrepresentable.
4. The background digest pass runs once per process, from one surface. app/…/AskViewModel.kt:161-168 is the only production caller of verifyStale. On a phone that keeps the process alive for days the check never repeats, and inactive packs are never re-hashed at all. The guarantee PackLibrary.kt:621-640 argues for — that a quotation is the book's bytes now, not at install time — decays accordingly.
5. Two pieces of process-global mutable state are reached from instance-shaped APIs. Library.supersessionCache and the Storage singleton (see Boundaries). Both are correct as written and both are invisible at the call site; the second one exists because a duplicate Store destroyed in-flight installs, which is the shape of bug this class of state produces.
Smaller things worth a look
  • AnswerCache.evict():174-181 re-runs size() and bytes() — two aggregate queries — on every loop iteration. Bounded by the 200-entry limit, so it is a papercut, not a defect.
  • PackLibrary.verify():600-619 issues its UPDATE outside a transaction; a crash between the hash and the write leaves verified_at stale, which fails safe (it re-verifies).
  • Router.generate returns Card.ModelUnavailable(availability = Availability.Ready) at :322-328 — the type name contradicts the state. See Glossary.
  • supersessionImpact opens and closes each target pack's SQLite file per call (PackLibrary.kt:449,464), inside the activation transaction. With many active packs this puts file opens on the critical path of a user-visible action.

Overloaded and misleading names

Card.ModelUnavailable is constructed with Availability.Ready. routing/…/Router.kt:319-328: when redaction empties the generation context, route 3 produces a ModelUnavailable card whose availability field is Availability.Ready and whose statement says the passages "cannot be separated from the rest, so they are listed rather than summarised" — nothing to do with the model. The behaviour is right (list the passages, generate nothing); the type name asserts something false about why. A reader debugging "why is the app saying the model is unavailable when it is loaded?" starts in the wrong place. Card.Listed, or a reason enum on the card, would say what is actually true.
"Gate" means four different things. All four are load-bearing and none is wrong on its own:
  • The activation gate — Packs.validate, the whole-pack validator (pack/…/Packs.kt:5-20).
  • Retrieval gates — Gates(lexical, dense, denseDefault), the admission thresholds (retrieval/…/Pipeline.kt:27).
  • InformationGate — the per-chunk query-coverage measure that feeds the lexical threshold.
  • Library.Gate — a private enum meaning "how much re-validation does this pack still need" (session/…/Library.kt:119).
In a doc comment or a commit message, "the gate" is ambiguous unless the sentence disambiguates it.
"Library" means three different things, in three different modules. session.Library is an opened set of validated packs (an AutoCloseable bound to a query's lifetime). state.PackLibrary is the durable shelf — installs, activation, leases. model.ModelLibrary is the set of downloaded weights. Their lifetimes are completely different (one query, forever, forever) and only the middle one is what a user would call "my library".
Post-rebrand naming residue. The app is now Ludex RPG and the package is dev.ludex, but the generic rpg prefix survives in three places that were deliberately left alone because changing them is not a rename:
  • .rpgpack and .rpgdoc — file format extensions. Changing them breaks every pack and exported sheet already in existence, and the format is documented under those names in docs/00-pack-schema.md.
  • RPG_CONTEXT — the context-window environment variable read at cli/…/Main.kt:87. Renaming it to LUDEX_CONTEXT is a one-line change plus a README note, but it is a user-facing interface change rather than a rebrand.
  • rpg-helper in git history before 0c217cb — the old name is still the truth about what those commits said.
Where naming is genuinely good, and worth preserving. Retrieved.refused reads as the domain concept ("refusal is a correct answer") rather than as isEmpty(). Candidate.verbatim encodes the two-column rule as one property. InstallResult.NeedsConfirmation / ActivationResult.NeedsAcknowledgement distinguish two different user questions that a boolean would have collapsed. PackForge.relax() names exactly why it exists — the honest attack is a builder that never wrote the CHECK constraint.
