An offline rules reference whose one promise is that you can always tell a quote from a paraphrase

An Android app that answers questions about tabletop RPG books you own, entirely on-device. A .rpgpack is a SQLite file someone else compiled from a book; the app treats it as untrusted input, narrows to passages without altering them, and decides mechanically whether a question is answered by showing the book or by speaking about the book. A generative model may write prose only from setting text, only with citations, and only where its claims can be checked against the passages it cites.

Refusal is a correct answer. The system is built to say I don't have that rather than to fill a gap — a plausible answer that isn't in the book is the exact failure this product exists to prevent. Ten Kotlin/JVM modules compose into an APK without any of them importing an Android class, except :app itself.

Key decisions

One SQLite binding, chosen once

pack/.../Sqlite.kt resolves to BundledDb (androidx.sqlite) for reads and StateDb uses the same driver for writes. JdbcDb survives only as an independently written second implementation for BundledDbTest to disagree with. Two tests refuse java.sql anywhere in a shipped module.

The cache has no invalidation logic

Keyed on the resolved query + (pack_uid, file_sha256) in priority order + model id + contract version. Content-addressed, so nothing needs to remember to invalidate anything.

The feed is the conversational window

No hidden context. What is on screen is exactly what a follow-up resolves against, and New topic clears both in one statement (Conversation.newTopic).

Refusal has its own path

The information-content gate measures the share of a query's summed IDF that candidates cover; when gating leaves nothing, Card.Empty is the answer. RRF scores are rank functions, so they carry no absolute quality signal — the gates are the only place holding one.

Three flows where correctness is the product

1 — A question becomes cards

sequenceDiagram
  participant U as User
  participant VM as AskViewModel
  participant L as Library.openActive
  participant S as AskService
  participant P as Pipeline
  participant R as Router
  U->>VM: ask(question)
  VM->>L: open active set (per question)
  L->>L: borrow lease + openCheck per pack
  Note over L: full gate NOT re-run — install already gated these bytes
  VM->>S: ask(question, library, render)
  alt model ready and query reads dependent
    S->>S: normalize against last 3 turns
  end
  S->>P: retrieve(resolved)
  P-->>S: candidates (or none)
  alt a setting/source candidate exists
    S->>S: cache lookup, keyed on (query, pack digests, model, contract)
    S-->>U: stored render, answer = null
  end
  S->>R: route(retrieved)
  R-->>S: cards
  S->>S: store only if a Generated card came out
  S->>S: record turn in the feed
  S-->>VM: Asked
  VM->>L: close (releases leases)
Seams.
  • AskService.kt:119 — the cache is consulted before routing, because routing is what invokes the model. Consulted after, it would pay the cost it exists to avoid while still looking like a cache.
  • AskService.kt:158 — the feed is written after the answer exists. A query that throws must not leave a turn the next follow-up resolves against.
  • AskViewModel.kt:107 — the active set is opened per question, so a pack activated in Settings takes effect on the next question rather than the next launch. The cost is one open per question; the gate is skipped there deliberately (Library.Gate.ALREADY_INSTALLED).
  • unverified on device Nothing in this flow has run on Android hardware. The bundled SQLite is exercised on the JVM only.

2 — Installing an untrusted pack

sequenceDiagram
  participant C as Caller
  participant PL as PackLibrary.install
  participant F as filesystem
  participant G as Packs.validate
  C->>PL: install(source, confirmReplacing)
  PL->>PL: journal row, state=installing
  PL->>F: copyBounded(source, staged)
  Note over PL,F: bytes that arrive, not the size claimed
  PL->>G: preflight then full gate, on the staged copy
  alt refused
    PL->>F: delete staged, delete row
    PL-->>C: Rejected / TooLarge
  end
  PL->>PL: readMeta + build_report + sha256, all from staged
  PL->>PL: transaction: re-read the row being replaced
  alt it changed while we verified
    PL-->>C: error, nothing installed
  end
  PL->>PL: measure supersession impact, excluding the pack being replaced
  PL->>PL: swap old row out, new row in
  PL->>F: delete old file when unread
  PL-->>C: Installed(pack, deactivatedForReview, impact, buildNotes)
Seams.
  • PackLibrary.kt — every decision derives from the staged copy, never from source. On Android the source is a content:// URI backed by another app, which can change between two reads.
  • Past the commit the swap is the installation. A failure deleting the old file must not unwind it, or neither pack would be installed.
  • A replacement inherits activation only if it does not newly hollow out another active book — otherwise it installs inactive, because activation is the step that requires acknowledgement.

Seams.
  • The gate runs before the move. Validating after meant a failed build had already destroyed the last known-good artifact — the loss staging exists to prevent, arriving through the one door staging did not cover.
  • :builder is the only shipped-adjacent module allowed to use JDBC; it is a desktop tool and NoDesktopBindingInProductionTest exempts it by name.
  • The gate cannot re-check the judge's work — no frontier model, no source document on the device. That claim travels as build_report and is surfaced at install, labelled as a claim.

Concurrency

StateDb serializes every use of its one connection behind a reentrant lock, because autoCommit and the current transaction are connection-wide state rather than per-caller state — two threads sharing it are not two writers. PackLibrary guards lease counts and pending deletions under a second lock, and condemnation plus unlink happen under it together so borrow cannot hand out a lease on bytes that are about to vanish. The Android path does its work on Dispatchers.IO and mutates Compose state only after.

Designed, not tested. No test in the repository runs two threads. The locking is argued for in comments and never exercised.

Risk ranking

1 — Nothing has run on an Android device. The bundled SQLite, the Compose tree, the file paths, the lifecycle are all exercised on a JVM or not at all. The APK assembles; that is the entire evidence. likely × wide
2 — :app has zero tests, and it is where every UI defect this session was found: the feed rendered behind a full-screen input, the roll control that could not be tapped, the missing New topic, the quotation rule that stopped partway down at accessibility text sizes. All four were review findings, not test failures. likely × narrow-but-visible
3 — The generative half is tested only against stand-ins. HashingEmbedder has no weights and the judges are hand-written. The plumbing is proven; the 0.65 dense gate is calibrated for the stand-in and there is no reason to think it transfers. certain × deep
